# API Review Findings (airport_tool_brief.md)

- High - Endpoint coverage is below the brief: FlightsController only supports create/update/delete with no list/search/pagination for date/airline/route (AMT.Api/Controllers/FlightsController.cs:12,38,64); SchedulesController lacks list/filter routes for clients/staff (AMT.Api/Controllers/ScheduleController.cs:13,27); TicketsController only exposes by-flight GET plus create/inventory/delete with no full CRUD or paged availability list (AMT.Api/Controllers/TicketsController.cs:14-57); BookingsController misses cancel and lookup by confirmation code (only id-based GET/DELETE) (AMT.Api/Controllers/BookingController.cs:28,44).
- High - Booking rules from the brief are not enforced: BookingService allows zero/negative quantities and never restores inventory on cancellation (delete just removes the record) (AMT.Application/Services/BookingService.cs:15-108); no overbooking or confirmation-code uniqueness enforcement; passenger email/name validation is absent; GET uses booking id instead of confirmation code, so client lookup scenario fails (AMT.Application/Services/BookingService.cs:115-120).
- High - Bulk import deviates from requirements: import reads the entire file into a string and never checks size (2MB) or row count (1000) limits (AMT.Api/Controllers/ScheduleController.cs:63-86); per-row validation/results are lost because BulkImportResultDto.ImportResults is keyed only by status, so multiple rows collapse into one entry (AMT.Application/Services/ScheduleService.cs:17-63); no 207 partial success payload and no transaction isolation per row.
- High - Business-rule validation gaps: no gate overlap or aircraft/gate availability checks when creating schedules (AMT.Application/Services/ScheduleService.cs:122-160); ticket pricing/inventory positivity not validated (TicketValidator only checks fare class/currency) (AMT.Application/Validators/TicketValidator.cs:11-19); booking validator only checks quantity <= inventory, allowing zero/negative quantities and no overbooking prevention (AMT.Application/Validators/BookingValidator.cs:10-14); flight number format/uniqueness not enforced and default aircraft is required despite being optional per brief (AMT.Application/Validators/FlightValidator.cs:9-20; AMT.Application/Dtos/CreateFlightDto.cs:21).
- Medium - Error handling and API shape diverge from brief: no global exception/problem-details middleware (Program.cs TODO) (AMT.Api/Program.cs:53); controllers hand-roll status bodies and may leak exception messages; options pattern not used for configuration; many synchronous repository reads despite async guidance.
- Medium - Staff stats and client-facing search/availability scenarios are missing: no /api/stats endpoint and no exposed search that combines schedules and ticket availability for clients (no controller/service entry points beyond by-id lookups).
- Medium - Data integrity and persistence hygiene: no EF Core migrations or index definitions checked into the repo; uniqueness for flight numbers and booking confirmation codes is not enforced in services, increasing conflict risk.
- Medium - Testing requirements unmet: there is no xUnit/Moq test project; no controller/service/repository tests or IFormFile import tests, so acceptance criteria for unit testing and ~70% coverage are not addressed.
