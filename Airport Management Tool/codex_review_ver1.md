# API Review Findings

- High - Flights endpoints missing reads and state toggles; only POST/PUT/DELETE exist (AMT.Api/Controllers/FlightsController.cs:12,38,64) so no GET /api/flights filtering/paging or activate/deactivate PATCH to meet Features.md flights scenarios.
- High - Flight validation doesn't enforce flight-number pattern/uniqueness and makes default aircraft mandatory; CreateFlightDto requires DefaultAircraftTail (AMT.Application/Dtos/CreateFlightDto.cs:21) and validator requires non-null (AMT.Application/Validators/FlightValidator.cs:17) despite spec saying optional; services never check duplicate flight numbers or airline+number uniqueness or pattern (AMT.Application/Services/FlightService.cs:11-63), nor return 409 on conflicts.
- High - Schedule coverage gaps: controller only supports GET by id and upcoming stats (AMT.Api/Controllers/ScheduleController.cs:13,27) with no list/filter endpoint; creation path ignores gate/aircraft availability or UTC/gate-overlap rules (AMT.Application/Services/ScheduleService.cs:122-160). Bulk import takes arbitrary JSON without size/row limits or per-row status, so cannot return 207 with partial results (AMT.Api/Controllers/ScheduleController.cs:63-86; AMT.Application/Services/ScheduleService.cs:17-63).
- High - Booking behavior deviates from scenarios: GET endpoint expects int and GetBookingByCode actually looks up by booking Id (AMT.Api/Controllers/BookingController.cs:28-36; AMT.Application/Services/BookingService.cs:115-120), so confirmation-code lookup fails. No cancel endpoint or seat-inventory restoration; delete just removes booking (AMT.Application/Services/BookingService.cs:95-108). Creation permits zero/negative quantities and ignores passenger name/email length, confirmation-code uniqueness, or ticket/schedule alignment (AMT.Application/Services/BookingService.cs:15-90; AMT.Application/Validators/BookingValidator.cs:12).
- Medium - Tickets feature gaps: API only exposes by-flight lookup/create/inventory/delete (AMT.Api/Controllers/TicketsController.cs:14-57) so no paged/filterable GET /api/tickets or full PUT /api/tickets/{id}. Validation allows negative prices/inventory because TicketValidator only checks fare class and currency (AMT.Application/Validators/TicketValidator.cs:11-19) and services don't enforce the BasePrice/Taxes/SeatInventory >=0 rules (AMT.Application/Services/TicketService.cs:15-55). Delete responds BadRequest instead of 409 when bookings exist (AMT.Application/Services/TicketService.cs:56-78).
- Medium - Stats endpoint absent: no /api/stats controller/service implementing staff summary scenario.
- Medium - Error handling/validation pipeline incomplete: exception middleware is TODO (AMT.Api/Program.cs:53) and there is no centralized problem-details response; model validation attributes on DTOs/domain (e.g., prices, passenger lengths) are not integrated into responses, so invalid inputs likely return 500s or custom payloads inconsistent with spec.
